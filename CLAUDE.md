# NexLift - Claude Code Guide

## Project Overview
NexLift is a PWA gym tracking app. Mobile-first, OLED dark theme. Built with React 18 + Vite + Tailwind CSS 4 (frontend) and Express.js + Prisma + PostgreSQL (backend).

## Architecture
```
client/          → React frontend (Vite)
  src/pages/     → Page components (Dashboard, Workout, Progress, etc.)
  src/components/→ Reusable components (goals/, layout/, ui/)
  src/services/  → API client functions
  src/context/   → React context providers
  src/data/      → Static data (exercises.js)
server/          → Express.js backend (ÚNICO backend, dev y prod)
  src/index.js   → Main server entry (sirve también client/dist en prod)
  prisma/        → Prisma schema & migrations
```
Backend único: `server/src/index.js` es el único backend. El antiguo `api/` (serverless de Vercel) y `shared/` fueron eliminados al migrar el deploy a Docker en VPS.

## Key Commands
```bash
cd server && npm run dev     # Start backend
cd client && npm run dev     # Start frontend
cd server && npx prisma studio  # View DB data
```

## Prisma: usar `db push`, nunca `migrate`
No existe `server/prisma/migrations/` — el schema siempre se ha sincronizado con `npx prisma db push`. Correr `prisma migrate dev`/`migrate deploy` falla con "drift detected" y ofrece resetear TODO el schema (pérdida total de datos) porque no hay historial de migraciones contra el que reconciliar. Para cualquier cambio de schema: `cd server && npx prisma db push` (y `npx prisma generate` aparte si el server estaba corriendo — Windows bloquea el archivo del query engine).

## Deploy (VPS + EasyPanel + Docker)
- `Dockerfile` (raíz): build multi-stage → compila el cliente, genera Prisma y arranca `server` (que sirve `client/dist` + API en el mismo puerto).
- **Variables de entorno obligatorias en EasyPanel:** `DATABASE_URL`, `JWT_SECRET` (el server NO arranca en producción sin `JWT_SECRET`), `NODE_ENV=production`. Opcional: `PORT`.
- **Variables opcionales (nuevas funciones, degradan sin romper si faltan):** `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT` (Web Push de recordatorio de descanso — sin ellas, `scheduleRestReminder` es no-op), `OPENAI_API_KEY` (deduplicación de ejercicios al importar rutinas — sin ella, cae al matching determinista por `canonicalExerciseKey`), `CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET` (avatar/fotos de progreso — sin ellas, `uploadPhoto()` cae a Catbox como antes). Ver `server/.env.example`.

## Design System
- OLED black (`#0a0a0a`), card bg (`#141414`), primary violet (`#8b5cf6`)
- All UI is mobile-first, dark theme only

## Modales: siempre con `<Portal>`
Cualquier overlay `fixed inset-0` (modal, visor de foto, selector) DEBE envolverse en `client/src/components/ui/Portal.jsx` (`createPortal` a `document.body`). Razón: las animaciones de entrada (`animate-fade-in`/`slide-up`/`scale-in`, en `index.css`) usan `transform` con `animation-fill-mode: forwards`, que deja el elemento marcado como transformado para siempre (aunque visualmente no se note) — eso convierte a cualquier ancestro animado en el *containing block* de sus descendientes `position: fixed`, sacándolos de "fijo al viewport" y dejándolos posicionados como si fueran parte del contenido con scroll. Sin `Portal`, un modal nuevo se ve bien al probarlo sin scroll y se rompe (aparece cientos de píxeles fuera de pantalla) en cuanto la página tiene scroll real.

## Date Handling
- DB stores UTC. Frontend must convert to local for display.
- Use `date.toLocaleDateString('sv')` (ISO format) when sending dates to backend.
- **Backend: la app es de un solo usuario, siempre en América/Ciudad de México, pero el contenedor corre en UTC.** Cualquier cálculo de "qué día es" (streak, heatmap, ventanas de "hoy", filtros por día de semana) DEBE pasar por los helpers de `server/src/logic.js` (`mexicoCityDateStr`, `mexicoCityDayBounds`, `mexicoCityHour`, `dayOfWeekFromDateStr`) — nunca `new Date()` ni sus accesores locales directo. Este bug se "arregló" 3 veces en distintos endpoints antes de resolverse por completo en un solo lugar; si agregas un endpoint nuevo que agrupe por día, usa estos helpers desde el inicio. Desde v2.5.0 estas funciones (y el resto de la lógica pura: Smart Loading, plateau, fase de rutina) viven en `server/src/logic.js` con tests en `server/src/logic.test.js` (`npm test` en `server/`) — extraídas literalmente de `index.js`, mismo comportamiento.

## Sesión y autenticación
- JWT con `tokenVersion` embebido: cambiar la contraseña o la pregunta de seguridad incrementa `User.tokenVersion` e invalida todos los tokens emitidos antes (`authMiddleware` lo compara en cada request). Esas dos rutas devuelven un `token` nuevo en la respuesta — el frontend debe persistirlo (`AuthContext.updateToken`) o la sesión actual se cierra sola.
- Tokens duran 365 días a propósito (se pegan una vez en un Atajo de iOS y no se renuevan) — la revocación real depende de `tokenVersion`, no de la expiración.
- Rate limiting en memoria (`rateLimit()` en `index.js`) — soporta un `keyFn` opcional para limitar por cuenta además de por IP (usado en recuperación de contraseña).

## Recordatorios (Web Push)
- `scheduleRestReminder`: aviso de fin de descanso. Se dispara por CADA serie individual marcada completada en `Workout.jsx` (vía `POST /api/workouts/rest-reminder`, llamado desde un único `useEffect` en `Workout.jsx` que compara el estado de `sets` contra un snapshot del render anterior — no desde `updateSet`/`toggleComplete` directamente, porque leer una variable seteada dentro del updater de `setSets(prev => ...)` justo después de llamarlo NO funciona: React difiere la ejecución del updater a la fase de render). El endpoint es independiente de `POST /api/workouts/log` (que guarda TODAS las series de un ejercicio en una sola llamada) precisamente para no tener que rediseñar cómo se persisten los datos solo para poder avisar por serie.
- **Dedup por usuario+ejercicio:** `scheduleRestReminder` mantiene un `Map` en memoria (`pendingRestReminders`, clave `` `${userId}:${exerciseId}` ``) y cancela (`clearTimeout`) cualquier recordatorio pendiente de la misma clave antes de agendar uno nuevo. Sin esto, completar 2+ series casi juntas (ej. registrando series olvidadas de golpe) agendaba un `setTimeout` independiente por cada una y el usuario recibía un push por cada una (el `tag` del service worker solo deduplica la notificación VISIBLE, no evita que el servidor mande varias).
- **Persistente desde v2.5.1 (modelo `PendingReminder`):** además del `setTimeout` en memoria, `scheduleRestReminder` hace `upsert` de una fila `PendingReminder` (mismo `@@unique([userId, exerciseId])` que el dedup de arriba). Al arrancar, `restorePendingReminders()` (llamado desde `startServer()`) lee lo que quedó pendiente de un redeploy/reinicio anterior: futuro → reagenda con el tiempo restante exacto; vencido hace <5min → dispara ya; más viejo → descarta sin avisar. Antes de esto, un redeploy a mitad de un descanso perdía el push en silencio — con deploys frecuentes en EasyPanel pasaba en la práctica.
- **Texto correcto al cambiar de ejercicio:** si la serie recién completada era la ÚLTIMA del ejercicio actual, el aviso debe mencionar el ejercicio SIGUIENTE, no el actual. `Workout.jsx` (`triggerSetCompleted`) calcula `sets.every(s => s.completed)` y, si aplica, resuelve `workoutState.exercises[currentIndex + 1]` y manda su nombre como `nextExerciseName` a `POST /api/workouts/rest-reminder`, que lo reenvía a `scheduleRestReminder` para componer el texto. Si no hay siguiente ejercicio (fin del día), cae al nombre del ejercicio actual.
- El temporizador visual en pantalla (`useRestTimer`, `Workout.jsx`) es la fuente principal (el push es respaldo, poco fiable en iOS Safari/PWA) y se basa en un timestamp absoluto (`Date.now() + segundos`), no un contador de ticks — recalcula contra la hora real en cada tick y al volver de segundo plano (`visibilitychange`/`focus`/`pageshow`), para no quedarse "congelado" mientras la app estuvo en background.
- **El snapshot de detección debe sincronizarse al cargar datos ya guardados:** `loadExerciseData` compara `sets` contra `prevSetsSnapshotRef` para saber si "una serie se acaba de completar". Si `setSets(...)` carga series YA completadas (desde el historial de hoy o desde el caché de `localStorage`) sin también actualizar `prevSetsSnapshotRef` en el mismo golpe, el efecto las lee como "recién completadas" y dispara un `triggerSetCompleted()` fantasma (timer visual reiniciado + push real) solo por abrir o revisitar la página — encontrado en vivo verificando el fix de sesiones parciales del Atajo. Cualquier rama de `loadExerciseData` que llame `setSets` con datos preexistentes debe actualizar `prevSetsSnapshotRef.current` a juego en la misma pasada.
- `checkReengagementReminders` (revisa cada 30 min): infiere la hora habitual de gym del usuario desde su historial real y manda "¿no vas a entrenar hoy?" si lleva 3+ días sin registrar nada, esa hora, máximo una vez al día (`User.lastReengagementNotifiedAt`).
- Todo lo anterior (excepto el temporizador visual) es no-op si `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` no están configuradas. El service worker (`sw.js`) usa `tag: rest-${exerciseId}` + `renotify: true` para que un aviso nuevo del mismo ejercicio reemplace al anterior en vez de apilarse.

## Atajo de iOS (shortcuts) y sesiones parciales
- `POST /api/shortcuts/log-set` registra UNA serie a la vez, acumulando en el `WorkoutLog` de hoy de ese ejercicio si ya existe uno (nunca fragmenta). Esto significa que un ejercicio puede tener un log de hoy con MENOS series que `Exercise.targetSets` — `Workout.jsx` (`loadExerciseData`/`checkCompletedExercises`) lo detecta comparando `sets.length` contra `targetSets` (no solo "¿existe un log hoy?") y muestra las series ya guardadas + filas vacías hasta completar la meta, todo editable (no se bloquea hasta llegar a `targetSets`). Al guardar, usa `PUT /api/workouts/:logId` (reemplaza todas las series del log, mismo endpoint que `EditSession.jsx`) en vez de `POST /api/workouts/log` (que SIEMPRE crea un log nuevo) — evita terminar con 2 `WorkoutLog` para el mismo ejercicio/día.
- **Convención de RIR — fácil de romper de nuevo:** `SetLog.rpe` no guarda el RIR crudo pese al comentario del schema (`// RIR`) — guarda `10 - RIR`. `Workout.jsx` convierte en los dos sentidos (`rpe: 10 - rir` al guardar, `rir: 10 - rpe` al leer). El Atajo pregunta "RIR?" (crudo, 0-4) y lo manda bajo el nombre `rpe` — `POST /api/shortcuts/log-set` debe aplicarle la misma conversión (`convertShortcutRir()` en `server/src/logic.js`, `10 - rpe_recibido`) antes de guardar, o el valor queda invertido y no calza con ningún botón de RIR (0-3) en la UI. Corrección retroactiva de datos ya guardados mal: `server/fix-shortcut-rir.mjs` (dry-run por defecto, `--apply` para escribir).

## Images
No binary storage. Frontend → Base64 → Backend → `uploadPhoto()` → URL stored in DB. `uploadPhoto()` (server/src/index.js) uses Cloudinary if `CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET` are configured (más confiable, con SLA), si no cae a la API de Catbox.moe (host anónimo gratuito, sin garantías — reintenta 3 veces antes de darlo por fallido). Migración de fotos existentes en Catbox hacia Cloudinary: `server/migrate-catbox-to-cloudinary.mjs` (correr una vez que las credenciales de Cloudinary estén en `.env`).

## Backup automático (v2.5.0)
Job diario (~04:00 CDMX, mismo patrón `setInterval` que `checkReengagementReminders`) exporta rutinas+workoutLogs+bodyLogs+personalRecords+goals+restLogs por usuario a JSON y lo sube a Cloudinary como recurso `raw`+`authenticated` (NO público — a diferencia de las fotos) en `nexlift-backups/`, con retención de los últimos 14. No-op sin credenciales de Cloudinary, mismo criterio que `uploadPhoto()`. Excluye a propósito `passwordHash`/`securityAnswerHash` (el JSON vive en un CDN de terceros). `POST /api/backup/run` (autenticado) fuerza una corrida para el usuario del token; `GET /api/health` expone `backup.users[].lastBackupAt/lastBackupError`. Restaurar: `server/restore-backup.mjs` (dry-run por defecto, `--apply` para escribir, idempotente vía upsert por id) — el usuario destino debe existir ya en la DB (mismo username). Ver sección "Backup y restauración" en `README.md`.

## Registro offline con cola de sincronización (v2.6.0)
`client/src/services/offlineQueue.js` (almacenamiento puro en localStorage, sin red) + `client/src/services/api.js` (red + reintento). Alcance: SOLO `logWorkout`/`updateWorkoutSession`/`logRestDay` — nada de fotos/goals/rutinas.
- `safeFetch` marca `err.isNetworkError = true` cuando `fetch()` mismo revienta (offline/DNS/timeout) — así se distingue de un 4xx/5xx real (que llega como `Response` normal, no como excepción). `api.logWorkout`/`updateWorkoutSession`/`logRestDay` capturan solo ese caso y encolan (`enqueueWrite`) en vez de perder el registro, devolviendo `{ queued: true }` — los callers (`Workout.jsx`, `Dashboard.jsx`, `EditSession.jsx`) deben chequear ese flag para avisar "Guardado local — pendiente" en vez de fingir éxito.
- **Anti-duplicados (el POST sí pudo haber llegado, solo se perdió la respuesta):** antes de reintentar un `logWorkout` encolado, `GET /api/workouts/today-log?exerciseId=X` (nuevo, usa `mexicoCityDayBounds` server-side) revisa si ya existe un log de hoy — si existe, convierte a `PUT` sobre ese log. **Bug real encontrado y corregido en vivo verificando esto:** la primera versión mandaba una fecha calculada en el navegador (`toLocaleDateString`) contra el endpoint genérico de historial (que filtra con `new Date(dateFrom)`, UTC ingenuo) — fallaba exactamente en la ventana de 6pm-medianoche CDMX (horario de gym) y creaba un log duplicado. El endpoint dedicado, con los helpers CDMX, lo evita.
- **Otro bug real encontrado en vivo:** `getQueue()` notificaba a los suscriptores (`subscribeQueueChange`) en cada simple lectura (para persistir la poda de items >48h) — un suscriptor típico (el badge de `Workout.jsx`, que llama `hasPendingWrite` → `getQueue` de vuelta) entraba en recursión infinita y reventaba el stack. Fix: la poda se persiste silenciosa (`writeQueueSilent`, sin notificar); solo mutaciones reales (`enqueueWrite`/`removeFromQueue`) notifican.
- Reintento: `replayOfflineQueue()` (en `api.js`) corre al abrir la app (código de nivel de módulo) y en el evento `online` de `window`. Errores de red o 401 durante el replay detienen el drenado (se reintenta después, sin descartar nada); cualquier OTRO error (validación real) sí saca el item de la cola — no reintenta infinito.
- Badge visible en `Workout.jsx` (`hasPendingWrite`/`subscribeQueueChange`) mientras el ejercicio afectado tenga algo pendiente.

## Auditoría de rendimiento (v2.6.1)
Medido contra la cuenta real (fernando.segrr, 281 WorkoutLogs / 794 SetLogs), solo lectura vía Prisma directo:
- `getWorkoutHistory(500)` (Dashboard/Progress): 246.7KB, 281 items — bajo el umbral de 500KB del plan, pero crece sin límite con el historial; vigilar si sigue creciendo (candidato futuro: endpoint de agregación server-side para plateau/1RM en vez de mandar cada set).
- `GET /api/routines`: 20.4KB (3 rutinas).
- Los tiempos absolutos medidos (~500-600ms por query) están inflados por la latencia de red dev-machine→VPS remoto (Postgres no está en la misma red que el entorno de desarrollo) — no representativos de prod (server y DB en el mismo VPS). La comparación RELATIVA sí es válida.
- **Fix aplicado (bajo riesgo, mecánico):** `GET /api/stats/overview` (7 queries) y `GET /api/stats/consistency` (3 queries) corrían en `await` secuencial pese a ser mutuamente independientes — cambiadas a `Promise.all`. Medido contra datos reales: 994ms → 522ms (~47% menos) en `/api/stats/overview`. Cero cambio de comportamiento (verificado con datos sintéticos: streak, `weeklyVolume` y días de descanso automáticos calculan igual).
- Build de producción (`npm run build` en `client/`): code-splitting sigue efectivo — recharts (`CartesianChart`/`XAxis`/`index.es`, ~275+56+158KB), jsPDF (~386+31KB) y html2canvas (~201KB) quedan en chunks separados, cargados solo al visitar Progress/ExportReport. Chunk inicial: 292.92KB raw / 91.69KB gzip (línea base de v2.0.0 era ~272KB raw — crecimiento ~8% tras varias features, razonable).
- Lighthouse (`npx lighthouse`, build de producción, página de login): Performance 83 (móvil, throttled) / 100 (desktop), Best Practices 100, SEO 92, Accessibility 68. La categoría "PWA" ya no existe en Lighthouse stock desde v9+ (removida del core). Accesibilidad NO se tocó (fuera del alcance de esta auditoría de performance) — hallazgos para una futura pasada: botones sin `aria-label`, `user-scalable=no` en el viewport (bloquea pinch-zoom), touch targets pequeños.
- N+1 encontrado pero NO corregido (fuera del alcance — endpoint raro, no "caliente"): `DELETE /api/routines/:id` hace un `workoutLog.count()` por cada ejercicio de la rutina en un loop anidado.

## Entrenador inteligente (plateau, mesociclos, descarga adaptativa)
- **Plateau:** `detectPlateau(sessions)` en `client/src/utils/exerciseName.js` — últimas 4-6 sesiones, si la mitad reciente no supera a la mitad antigua en 1RM estimado, se marca. 100% cliente (Progress.jsx y Dashboard.jsx ya traen `getWorkoutHistory(500)` para esto, sin endpoint dedicado). Al cruzar un `PersonalRecord` con el historial agrupado, usa siempre `canonicalExerciseKey(pr.exerciseName)` — `PersonalRecord.exerciseName` se guarda solo en `.toLowerCase()`, no con la normalización completa, así que un match de string crudo falla en silencio ante acentos/plurales/paréntesis.
- **Mesociclos:** modelo `RoutineBlock` (opcional por rutina — sin bloques, todo se comporta igual que antes). El bloque activo es el de `startedAt` no-nulo más reciente (calculado en lectura vía `getActiveBlock()`, sin `isActive` guardado que mantener). `phase` es un string libre (`accumulation`/`intensification`/`deload`/`custom`), no un enum de Prisma. CRUD en `POST/PUT/DELETE /api/routines/:id/blocks` + `POST .../blocks/:blockId/start`. UI en `EditRoutine.jsx` (crear/editar, guardado inmediato por bloque, no con el botón "Guardar" general) y `RoutineDetail.jsx` (ver + botón "Iniciar siguiente bloque").
- **Descarga adaptativa:** `getRoutinePhaseStatus(routine)` en `server/src/logic.js` es la **única** fuente de verdad para "¿en qué fase está esta rutina ahora mismo?" — devuelve `{ isDeload, source, phase }`; prioridad fija: cualquier bloque activo manda (su `.phase` tal cual), si no hay ninguno cae a `Routine.adaptiveDeloadUntil` (ventana de 7 días activada por `maybeEvaluateAdaptiveDeload`, que corre 1x/día vía `setInterval`, mismo patrón que `checkReengagementReminders` — este mecanismo standalone SOLO conoce `'deload'`, no hay forma de "acumular/intensificar automáticamente" sin un bloque configurado). Trigger adaptativo: volumen semanal `<85%` del anterior **y** `>=3` ejercicios de la rutina en plateau simultáneo — ambas señales a la vez, ninguna sola (números de primera aproximación, sin validar contra uso real).
- **`phase` ajusta la sugerencia en los dos algoritmos** (`computeSuggestion` cliente en `Workout.jsx`, `computeWorkoutSuggestion` servidor en `server/src/logic.js`, usado por `/api/shortcuts/next-set` — hay que tocar los dos siempre): `adjustRepRangeForPhase(lo, hi, phase)` (duplicada en `server/src/logic.js` y `client/src/utils/smartLoading.js`, con test de paridad) reduce el rango a la mitad en `intensification` (más peso, menos reps) o sube el techo 50% en `accumulation` (más reps antes de subir peso) — **sin tocar `Exercise.targetReps` guardado**, solo el rango usado para ESA sugerencia. `deload` además reduce el peso final ~10% (constante fija) tras aplicar la doble progresión normal. `custom`/sin fase activa: sin cambios, comportamiento idéntico a antes de esta feature. Aviso visible siempre en `Workout.jsx` vía el objeto `PHASE_BANNER` (banner + badge recoloreado, nunca un ajuste silencioso) — ojo con las clases de Tailwind ahí: deben quedar completas y literales en el código (`'bg-[var(--primary)]/10'`), nunca construidas con interpolación de string, porque el compilador de Tailwind no genera clases que no puede ver como texto literal.
- **Gotcha de duplicación:** el proyecto no comparte código cliente/servidor (`shared/` se eliminó a propósito, ver Backend único abajo). `detectPlateau`/`groupHistoryByExercise`/Epley ya estaban duplicados; esta feature agrega `detectPlateauForExercise` en el servidor (`server/src/logic.js`) como una 2ª copia deliberada (por id de ejercicio, no por nombre canónico — no hace falta consolidar variantes dentro de una sola rutina activa). Si se corrige un bug en la lógica de plateau, corregirlo en los dos lados — hay un test de paridad (`client/src/utils/smartLoading.parity.test.js`) que corre los mismos fixtures por ambas implementaciones para detectar justo esto.
